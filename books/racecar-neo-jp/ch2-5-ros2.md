## ③ 本文

### ROS 2 は「小さなプログラムの集まり」

ロボットのソフトウェアを、1つの大きなプログラムで書くのは大変です。カメラの読み取り、LIDAR の読み取り、ハンドルの制御……と、仕事がたくさんあるからです。

ROS 2 では、仕事ごとに小さなプログラムに分けます。これを**ノード**と呼びます。ノードどうしは、**トピック**という名前の付いた通り道を使って、データ（**メッセージ**）をやりとりします。

トピックは、ラジオの放送局のようなものです。

- データを送る側（**配信**する側）は、「`/scan` という局で LIDAR のデータを流します」と、決まった局に流すだけです
- データを受け取る側（**購読**する側）は、「`/scan` という局を聞きます」と、局に合わせるだけです
- 送る側と受け取る側は、おたがいを知らなくてかまいません。同じ局を何人でも聞けます

こうしておくと、LIDAR のドライバを別の部品のものに取り替えても、`/scan` に同じ形のデータを流しさえすれば、ほかのノードは何も変えずに済みます。

図1を、データの流れる向きにそってたどってみましょう。

**見る（センサ → あなたのプログラム）**

| トピック | 送るノード | 流れるデータ |
|---|---|---|
| `/camera/color`、`/camera/depth` | `realsense2_camera`（カメラのドライバ） | カラー画像、深度画像 |
| `/scan` | `sllidar_node`（LIDAR のドライバ） | LIDAR の1周分の距離 |
| `/imu/fused` | `imu_fusion_node` | カメラと基板の2つの IMU をまとめた値 |
| `/joy` | `joy_node`（ゲームパッドのドライバ） | ボタンとスティックの状態 |
| `/battery/voltage`、`/encoder/speed` など | `pit_node` | バッテリーの電圧、車輪の速さなど |
| `/edgetpu/inference` | `edgetpu_node` | Coral で見つけた物体（第9章） |

**動く（あなたのプログラム → モーター）**

1. あなたのプログラムが `rc.drive.set_speed_angle(速さ, 角度)` を呼ぶと、その命令が `/drive` に流れます
2. `mux_node` が、2-4 の安全の関所です。右バンパーが押されているときだけ、あなたの命令を先へ通します
3. `throttle_node` が、速さと角度に上限をかけます
4. `pit_node` が、命令を Teensy に送ります。ここから先は ROS 2 の外で、Teensy がモーターとサーボを動かします

あなたの命令は、モーターに届くまでに**必ず安全の関所を通る**ように作られています。

### あなたのプログラムと ROS 2 のつなぎ目

実機で `racecar_core` を使うと、その内側で、センサごとの小さなノードが作られます。たとえば LIDAR なら、`/scan` を購読するノードです。しくみを簡単にすると、次のようになっています。

```python:ライブラリの内側（簡単にしたもの）
import rclpy
from sensor_msgs.msg import LaserScan


class LidarReal:
    def __init__(self):
        self.node = rclpy.create_node("scan_sub")
        self.latest = None
        # /scan を購読し、メッセージが届くたびに callback を呼んでもらう
        self.node.create_subscription(LaserScan, "/scan", self.callback, 1)

    def callback(self, msg):
        self.latest = msg.ranges      # 届くたびに、最新の値で上書きしておく

    def get_samples(self):
        return self.latest            # あなたのプログラムは、最新の値を読むだけ
```

ここに、第2章のテーマだった**ポーリング**が出てきます。

- ROS 2 の世界では、データは**向こうから届きます**。届くたびにコールバックが呼ばれ、最新の値が上書きされます
- あなたのプログラムは、`update()` の中で `rc.lidar.get_samples()` を呼び、**しまってある最新の値を聞きにいきます**。これがポーリングです

「届いたデータをしまっておき、使う側は好きなときに最新の値を読みにいく」。こうすることで、あなたは ROS 2 のしくみを知らなくても、2-3 と同じ書き方でセンサを読めます。

### 同じプログラムが、シミュレータでも実機でも動くわけ

RACECAR のライブラリの中には、同じ名前の命令を持つ部品が、**シミュレータ用**と**実機用**の2種類ずつ入っています。

| あなたが呼ぶ命令 | シミュレータ用の中身 | 実機用の中身 |
|---|---|---|
| `rc.lidar.get_samples()` | シミュレータに「LIDAR の値をください」と問い合わせる | `/scan` から届いた最新の値を返す |
| `rc.controller.was_pressed(...)` | シミュレータに問い合わせる（2-1） | `/joy` から届いたボタンの状態を調べる |
| `rc.drive.set_speed_angle(...)` | シミュレータに命令を送る | `/drive` に命令を流す |

あなたのプログラムは、どちらの中身が使われているかを気にする必要がありません。**使う側から見た命令の形をそろえて、中身だけを取り替えられるようにする**のは、ソフトウェアを作るときの大切な考え方です。これのおかげで、シミュレータで作ったプログラムを、そのまま実機に持っていけます（ただし 2-3 で見たように、IMU の軸の向きや、実機でしか使えないセンサなどの違いには気をつける必要があります）。

## ⑤ つまずきポイント

### トピックの名前を1文字まちがえても、エラーにならない

ROS 2 では、まだ誰も配信していないトピックを購読しても、エラーにはなりません。データが届くのを、ただ待ち続けます。自分で ROS 2 のノードを書いて「データが来ない」ときは、まずトピックの名前（先頭の `/` も含めて）を確かめましょう。

### 「ROS」は OS ではない

Robot Operating System という名前ですが、Windows や Linux のような OS ではありません。Linux（RACECAR では Ubuntu）の上で動く、ロボット用のソフトウェアの部品と道具の集まりです。

## ⑥ 確認問題

**問1**　LIDAR のデータを配信しているノードと、そのトピックの名前を答えなさい。

:::details 答え
`sllidar_node` が、`/scan` というトピックに配信しています。
:::

**問2**　あなたのプログラムの命令が、`/drive` から直接 `pit_node` に行かず、`mux_node` を通るようになっているのはなぜですか。

:::details 答え
`mux_node` が安全の関所になっていて、人が右バンパーを押している間だけ、プログラムの命令を先へ通すためです。手動運転の命令とプログラムの命令のどちらを使うかも、ここで決めています。
:::

**問3**　ROS 2 ではデータが向こうから届くのに、あなたの `update()` では「聞きにいく（ポーリング）」形で読めるのはなぜですか。

:::details 答え
ライブラリの内側で、データが届くたびにコールバックが最新の値をしまっておくからです。`update()` は、そのしまってある最新の値を読みにいくだけで済みます。
:::
